ARCHITECTURE: How Kelvi AI Works

From spoken intent to real-world action

Kelvi AI separates voice processing from business logic. The runtime handles language, memory, state, tools, and safety, while applications define the actions they want to perform.

Indian-language first Tool-driven Provider-agnostic
1. High-Level Product Flow
Step 01
User speaks

Caller speaks in Malayalam, Hindi, or code-mixed speech over browser audio or phone.

Step 02
Understand intent

Kelvi AI transcribes the utterance, detects language, strips fillers, and resolves intent.

Step 03
Execute tool

A registered tool performs the required action (checking availability, booking, or tracking).

Step 04
Natural response

Kelvi AI generates localized voice output formatted with native prosody and accent.

Kelvi AI connects multilingual voice conversations to real-world actions such as checking availability, creating bookings, or retrieving order information.

2. Kelvi AI Runtime Architecture

Kelvi AI is not a hardcoded pipeline. It is a domain-agnostic runtime surrounded by replaceable provider adapters.

Kelvi AI is built around Gnani's Indian-language speech stack, while its adapter boundaries allow alternative providers or local models to be integrated later without altering application logic.

check_availability Resolves temporal slots in Malayalam and Hindi, suggesting nearest alternatives on conflict.
book_slot Locks slots atomically in PostgreSQL, preventing double-bookings during high concurrency.
Safety confirmation Enforces caller agreement before booking or cancelling, preventing accidental changes.

3. Hybrid Routing for Reliable Voice Interactions

Kelvi AI uses two paths for processing a conversation. Deterministic rules handle predictable inputs such as confirmations, cancellations, and common date or time expressions. More ambiguous inputs can be routed to the reasoning adapter for contextual interpretation. If the reasoning service is delayed or unavailable, the deterministic path provides a controlled fallback.

Fast Path

Common confirmations, dates, times, and slot responses are handled locally without unnecessary reasoning calls or credit consumption.

Reasoning Path

Ambiguous names, conversational context, and colloquial clarification can be passed to the configured reasoning adapter.

Safe Action Path

Tools validate inputs and require confirmation before sensitive actions such as creating or cancelling a booking.

Simple request → Fast path
Complex request → Reasoning path
Confirmed request → Tool execution

5. Reliability & Security Implementation Details

Explore the engineering safeguards that keep production voice sessions stable and secure:

Audio Validation & Payload Bounds
Audio uploads are capped at 10MB to prevent denial-of-service attempts. Incoming audio payloads are checked for standard RIFF/WAV headers, linear PCM sample rates (16kHz / 48kHz), and silence thresholds. Empty or corrupted chunks are intercepted before calling speech models.
PII Masking & Data Privacy
All caller phone numbers in database records, call events, and operations dashboards are automatically masked (e.g. +91 90000 ***01). Raw microphone audio is held in memory only during turn processing and is never persisted to permanent disk storage.
In-Memory Audio LRU Cache
Static openings, standard greetings, and repeated turn prompts are synthesized once and held in an in-memory LRU cache. Replays and duplicate turns are served instantly with zero synthesis latency and zero redundant speech credit consumption.
Telephony Signature Verification
Twilio telephony webhooks enforce cryptographic HMAC-SHA1 signature verification using the configured authentication token, protecting incoming call endpoints against forged or spoofed requests.
